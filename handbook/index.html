The Nerv Handbook

How to install Nerv, use it every day, and run it across many machines.

This machine

  1. Why an operating system, still

    This chapter is about why we bothered to build an operating system at all, when perfectly good ones already exist. It is a bit of history and a bit of opinion, and it is the reasoning behind most of the decisions you will run into elsewhere in this handbook.

  2. What Nerv is

    Nerv is a Linux distribution built from source for NVIDIA's Grace Blackwell machines. Like FreeBSD's base system, it is one tree, built together and versioned together; like Fedora, it is RPM-based and takes up new things early.

  3. Install

    Nerv installs over the network from any Linux machine you already have: one command turns that machine into the installer, and the GB10 you are installing boots from it, with no USB stick and nothing typed into the target.

  4. The first hour

    What you have once you log in: the console and the shell, the tools that replace the ones you know, where the defaults live and how to change one so an update keeps your change, plus becoming root, swap, printing, mail, memory, and checking the machine is well.

  5. Software

    Installing and removing programs with dnf: Nerv's own packages and the whole of Fedora's, the three kinds of package and what each allows, the stable and testing channels, where a package's settings live, and what happens to a package you install or a file you change once an update is waiting for its reboot.

  6. Containers

    Running containers with podman, as yourself and without root: what every container gets by default, Nerv's two base images and how they arrive, building on them, time zones in a container, running a container as a service, tools that expect Docker, which registries a machine pulls from and how to allow one, Fedora's images, and the GPU inside a container.

  7. The desktop

    Umbriel, Noctalia and foot, for machines that install one: getting a desktop, logging in, the keys you use, the shell around your windows, the browser, sound and the keyboard.

  8. Networking

    Getting on the network and letting others reach you: wired and Wi-Fi, names, the ConnectX ports, WireGuard, the firewall and SSH.

  9. Accounts and keys

    The people on a machine and how each proves who they are: accounts, the groups that grant the GPU, the desktop and root, security keys, the passwords you keep, and the disk's passphrase.

Five ideas

  1. Generations

    The system lives in slots, and an update never touches the one you are running. It builds a new slot beside it, proves that slot boots to a login, and puts it on trial: if it never completes a boot, the machine goes back to the one before by itself, and cage rollback goes back on your word.

  2. The compute fabric

    One boundary governs compute: your GPU, someone else's across the network, memory, and where programs run. Every program is a client, and everything is accounted. GPUs on several machines work together through the standard NCCL library.

  3. What the machine remembers

    MAGI, the machine's database of what it knows: everything observed on it, as a record that cannot be quietly changed, the facts that follow from that record, and answers that say exactly how far they can be trusted.

  4. Yours and not yours

    Your work, rebuildable residue, and unexplained bytes: Seele, which knows what on the machine is yours, what can be rebuilt, and what nothing accounts for, and what follows you to the next machine.

  5. The chain of trust

    What is verified between power-on and a prompt, what holds the machine to its rules once it is up, and precisely what all of that does not defend against.

Ways of using it

  1. AI development

    Running a language model on the machine with S2 and talking to it through OpenAI's API from any program, and PyTorch and CUDA in a container.

  2. Gaming

    Steam, titles built for x86, and borrowing a faster GPU from across the room.

  3. Offloading and fleets

    Putting work on other machines, and several boxes acting as one: the targets you name, serving a machine's GPU, running a program elsewhere, and what running a fleet for an organisation will add.

  4. Plexus

    Reaching your machines from anywhere: one authority you run yourself, machines that enrol with it, and access that exists only where you grant it.

  5. Building your own

    Packaging software for your machine, a repository to serve it from, systems of your own, and owning the stack from the source up.

When it breaks

  1. Recovery

    Rollback, the rescue slot, the morning it will not boot, the forgotten passphrase. Written for someone having a bad day: each section starts from what you see and ends with the machine working.

  2. Asking why

    From a symptom to a cause, using the machine's own record: a program that stopped, a service that will not start, something that was refused, and a machine that is slow.
